# Apex GP

**Play it:** https://davidcbradleyjr.github.io/apex-gp/

A browser F1 sim (time trial and short races) on three made-up circuits: Kestrel Valley (4.2 km, flowing), Virel Park Autodrome (5.0 km, long straights and big stops) and Callow Heath (4.0 km, tight and technical). Three views, including a first-person cockpit with a working steering-wheel display and mirrors. It uses three.js r147, and all of the audio is synthesized.

- `src/game.js` is the engine. It holds the track builder, the vehicle physics, timing, the renderer and audio. The physics covers per-wheel loads, aero, Pacejka-style tyres with temperature and wear, ABS/TC, an 8-speed gearbox, and ERS/DRS. This file is the source of truth.
- `design/project/` holds the Claude Design canvas. `Main.dc.html` is the playable game UI and `Garage.dc.html` is the car sheet. The `game.js` in that folder is a copy, so run `cp src/game.js design/project/game.js` before republishing.
- `assets/` holds the car concept image (Higgsfield GPT Image 2.6) and its 3D mesh (Tripo H3.1). `vendor/car.js` is that GLB encoded as base64.
- Three real layouts are included as well: Autodromo Nazionale Monza, Silverstone Circuit and Bahrain International Circuit. They are flat copies of the centre lines in the [TUM racetrack database](https://github.com/TUMFTM/racetrack-database) (LGPL-3.0, traced from OpenStreetMap), with a constant 13 m road width and auto-placed DRS zones; `node tools/import-track.js Track.csv [startShiftMetres]` prints the control points for another one. The autopilot laps them 3 to 10 s off real race pace (Monza 1:25, Silverstone 1:38, Bahrain 1:40).
- Teams are the `TEAMS` list in `src/game.js`: the 2026 grid by name, each a body colour and an accent colour painted into the one car model's texture (no logos). `create(canvas, { team })` or `game.team(id)` sets the player's car; in a race the AI cars take the other teams. All cars drive the same.
- Circuits are the `TRACKS` list at the top of `src/game.js`; the engine builds one per `create(canvas, { track: id })`, and the menu re-creates the game to change circuit.
- `src/index.html` is the standalone web page (menu and HUD in plain HTML and JS). `./build.sh` copies it, the engine and `vendor/` into `docs/`, which GitHub Pages serves from `main`. Update loop: edit, `./build.sh`, commit, push. It takes `?track=virel|callow&mode=race&cam=2&start=1` as a deep link.
- `src/play.html` is a bare local test page. Run `python3 -m http.server` in this folder, open `/src/play.html` (add `?track=virel` or `?track=callow`), and press Enter to start.
- `test/sim-test.js` is the physics check. Run `node test/sim-test.js`: an autopilot drives 3 laps, and the test asserts that lap time, speed and g-loads are plausible, that the car does not spin with assists on, and that every circuit laps cleanly. `node test/race-test.js` checks races.

## Sim rigs: Linux and Windows

Open **Controls → SIM RIG · WHEELS, PEDALS & FFB → Start input walkthrough** in the standalone game. It asks you to move one control at a time, detects the axis or button, and waits for your confirmation. Calibrate left/right/center, then released/full throttle and brake; optional steps assign paddles, DRS, overtake and pause. A turning wheel model, animated pedals, live 0–100% bars and button indicators let you verify each assignment. Pedal percentages represent pressure on load-cell pedals or travel on position sensors. Existing settings are kept until **Save rig setup**; Cancel or Escape discards the draft. **Advanced manual bindings** retains direct axis/button selection. Pedals may be separate USB devices, inverted, or share opposite halves of an axis. Calibration is saved locally. Wheel input is linear at every speed; configure the base for **360° total rotation**. Standard gamepads and keyboard controls remain available; turn wheel input off to use them while a calibrated rig is attached.

Browser input works wherever the browser exposes the device through its Gamepad API; move a control after connecting it. **This build uses the local SDL2 bridge for directional steering force feedback**. Controller vibration is not steering FFB. Direct browser FFB through WebHID is possible on compatible hardware, but is not implemented here yet; the GitHub Pages build currently supports wheel input without steering torque.

1. Install Python 3 and an SDL2 runtime. On Linux, install your distribution's SDL2 package (Arch: `sdl2-compat`, Debian/Ubuntu: `libsdl2-2.0-0`). On Windows, get the x64 SDL2 runtime DLL from the [official SDL2 releases](https://github.com/libsdl-org/SDL/releases?q=release-2), use 64-bit Python, and place `SDL2.dll` beside `tools/rig-bridge.py`. Alternatively pass `--sdl /path/to/library`. No Python packages are required.
2. Install/configure your wheel's normal OS driver. Windows Moza rigs use Moza's driver/Pit House; disable Steam Input for the wheel if it changes the device into a standard pad. Linux needs input-device read/write permission and a driver exposing constant-force effects; check the [Linux wheel support list](https://github.com/JacKeTUs/linux-steering-wheels) and [universal-pidff](https://github.com/JacKeTUs/universal-pidff) for your base/kernel. The bridge never installs drivers, changes permissions or claims unsupported hardware works.
3. From this repository run `python3 tools/rig-bridge.py` (Windows: `py -3 tools/rig-bridge.py`), then open **http://127.0.0.1:8766**. The bridge serves the built game from `docs/`; run `./build.sh` after source edits on Linux. This keeps game and hardware on one local origin. Browser and SDL axis numbering can differ, so calibrate again when switching between hosted and bridge play.
4. Calibrate, then explicitly enable **Steering FFB**. It starts off each visit. The default slider gives 5% of the base's full output; the bridge caps output at 20%. Start low and check that the wheel resists steering. If it pulls into a turn, disable FFB and toggle **Reverse FFB direction**. Strength and direction need real-hardware tuning; keep the base's emergency stop available.

FFB uses front-tyre lateral forces and an approximate pneumatic trail that drops with slip. It is an initial aligning-torque model; steering feel has not been tuned on a real base. Torque stops in menus, on pause/finish, loss of focus, missing mapped devices, stale simulation updates and bridge failure. Effects expire after 120 ms without renewal. Pause disarms FFB; **Resume with wheel FFB** explicitly re-enables it. Unplugging a mapped wheel or pedal pauses the session. Ctrl+C stops the bridge and releases its effects. Automatic centering is disabled when creating our effect; use your base software to restore your preferred centering afterward if needed.

Devices reporting no constant-force capability stay input-only. Calibration keys use device names/vendor/product and an occurrence number for identical devices; reconnect identical devices in the same order or recalibrate. This bridge targets desktop Linux and Windows; physical Moza/other-rig behavior and Windows execution remain unverified. Linux SDL startup and the local HTTP connection were verified with no connected rig.

Checks: `node test/rig-test.js`, `python3 test/rig-bridge-test.py`, plus the existing physics/race checks. `test/rig-wizard-ui-test.js` checks the guided flow, previews, cancellation and save/reload with simulated R3 inputs. `test/rig-ui-test.js` runs through Playwright's `browser_run_code_unsafe` tool with the bridge running; it supplies simulated devices and never commands physical hardware. The bridge listens only on loopback and checks Host/Origin on hardware commands.
